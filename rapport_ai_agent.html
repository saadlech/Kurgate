Agent IA Kurgate

Documentation Technique — Projet de Fin d'Études

1. Introduction et Contexte

L'agent IA de Kurgate est un assistant conversationnel intelligent intégré dans une application mobile de tourisme au Maroc. Il ne se limite pas à un simple chatbot de questions-réponses : c'est un agent autonome capable d'exécuter des actions concrètes (recherche, réservation, paiement, avis) en interagissant directement avec la base de données de l'application.

Distinction clé : Un chatbot répond à des questions. Un agent IA agit — il prend des décisions, appelle des outils, et modifie l'état du système de manière autonome.

4. Concepts Clés d'IA Utilisés

4.1 Large Language Model (LLM)

Le modèle utilisé est o4-mini d'OpenAI, déployé via Azure OpenAI Service. C'est un modèle de type reasoning (raisonnement) qui :

  • Comprend le langage naturel en français, arabe et darija
  • Raisonne sur les intentions de l'utilisateur
  • Décide quels outils appeler et dans quel ordre
  • Synthétise les résultats en réponse naturelle

Paramètres de configuration :

  • max_completion_tokens: 16000 — Limite de tokens pour la réponse
  • tool_choice: "auto" — Le modèle décide autonomement quand appeler un outil

4.2 Function Calling (Appel de Fonctions)

C'est le mécanisme central qui transforme un LLM en agent autonome. Le principe :

  1. On définit des schémas d'outils (JSON Schema) qui décrivent les fonctions disponibles
  2. Le LLM analyse la requête et décide quel(s) outil(s) appeler
  3. Le LLM génère les arguments structurés (JSON) pour chaque outil
  4. Le backend exécute les outils et retourne les résultats au LLM
  5. Le LLM synthétise les résultats en réponse naturelle
Référence académique : Le Function Calling correspond au paradigme ReAct (Reasoning + Acting) décrit par Yao et al. (2022) — "ReAct: Synergizing Reasoning and Acting in Language Models".

4.3 Prompt Engineering (Ingénierie de Prompt)

Le System Prompt est un texte d'instructions qui cadre le comportement de l'agent. Dans Kurgate, il définit :

  • L'identité : "Tu es l'agent Kurgate, assistant de tourisme au Maroc"
  • Les règles métier : processus de réservation en 4 étapes (A→D), confirmation obligatoire
  • Les contraintes : ne jamais inventer de données, toujours appeler les outils
  • Le format : répondre en français avec emojis, prix en MAD
  • Les capacités : liste exhaustive de ce que l'agent peut faire
  • Les interdictions : ne jamais prétendre envoyer des emails/SMS

4.4 Boucle Agentique (Agentic Loop)

L'agent fonctionne en boucle itérative (max 10 itérations) :

┌──────────────────┐ │ Message │ │ Utilisateur │ └────────┬─────────┘ ▼ ┌──────────────────┐ │ Envoyer au LLM │◄──────────────────┐ └────────┬─────────┘ │ ▼ │ ┌──────────────────┐ │ │ Le LLM veut │── Oui ──▶ Exécuter les outils │ appeler des outils?│ en parallèle ──────┘ └────────┬─────────┘ │ Non ▼ ┌──────────────────┐ │ Réponse finale │ │ au client │ └──────────────────┘

Points clés :

  • Exécution parallèle : Plusieurs outils peuvent être appelés simultanément (Promise.all)
  • Itérations multiples : Le LLM peut chaîner des appels (recherche → détails → réservation)
  • Garde-fou : Maximum 10 itérations pour éviter les boucles infinies

4.5 Gestion de la Mémoire Conversationnelle

La mémoire est gérée côté client (Flutter) :

  • Historique limité à 20 messages (fenêtre glissante)
  • Les 16 derniers messages sont envoyés au LLM pour garder le contexte
  • Session identifiée par un sessionId unique

6.2 Validation des données

  • Le user_id est validé par regex UUID (/^[0-9a-f-]{36}$/i) avant toute insertion
  • Les champs obligatoires sont vérifiés avant chaque écriture
  • Le user_id est injecté côté serveur (pas confié au LLM)

9. Justification des Choix Technologiques

9.1 Pourquoi Azure OpenAI (et non OpenAI directement) ?

  • Conformité entreprise : Azure offre des certifications (ISO 27001, SOC 2)
  • Résidence des données : Contrôle de la région de déploiement
  • SLA garanti : 99.9% de disponibilité
  • Intégration : Compatible avec l'écosystème Microsoft

9.2 Pourquoi Supabase Edge Functions ?

  • Serverless : Pas de serveur à gérer, mise à l'échelle automatique
  • Deno Runtime : Sécurité par défaut (sandbox), TypeScript natif
  • Proximité DB : Co-localisée avec PostgreSQL (latence minimale)
  • Coût : Facturation à l'utilisation

9.3 Pourquoi le modèle o4-mini ?

  • Raisonnement avancé : Modèle optimisé pour les tâches complexes multi-étapes
  • Function Calling : Support natif des appels de fonctions structurés
  • Rapport qualité/coût : Performances élevées à coût réduit
  • Multilingue : Excellent support du français, arabe et darija

9.4 Pourquoi la mémoire côté client ?

  • Simplicité : Pas de stockage serveur nécessaire
  • Vie privée : Les conversations ne sont pas persistées sur le serveur
  • Fenêtre glissante : Limite à 20 messages (contrôle des coûts tokens)
